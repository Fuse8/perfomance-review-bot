# Codebase Refactoring

Created: 2026-07-01

## Problem

Кодовая база растет, и часть логики может быть смешана: бизнес-правила, интеграции, форматирование сообщений, утилиты и инфраструктурный код не всегда очевидно разделены. Из-за этого сложнее безопасно менять workflow и добавлять новые сценарии.

## Desired Behavior

Код структурирован по понятным зонам ответственности. Лишний и устаревший код удален, повторяющаяся логика вынесена в утилиты, бизнес-логика отделена от интеграционного кода и форматирования output. Рефакторинг не меняет пользовательское поведение.

## Current Context

Задача большая и может потребовать декомпозиции на подзадачи после первичного аудита. Публичные API, auth flow, `TokenStorage` contract и local JSON mode должны оставаться стабильными, если отдельная задача явно не требует другого.

## Plan

- Провести аудит структуры `src/`, тестов и основных workflow.
- Найти дублирование, устаревший код, большие функции и смешанные ответственности.
- Зафиксировать список подзадач, если рефакторинг нельзя безопасно сделать одним небольшим изменением.
- Разнести общие helpers/utilities отдельно от бизнес-логики.
- Выделить границы между Google API-интеграциями, workflow orchestration, chat output и доменными правилами.
- Удалить неиспользуемый код после проверки ссылок и тестов.
- Делать изменения небольшими шагами с сохранением текущего поведения.

## Tests

- `pnpm format`
- `pnpm eslint:fix`
- `pnpm type-check`
- `pnpm test:quiet`
- Для каждой подзадачи добавить или обновить точечные тесты, если меняется внутренняя структура важного workflow.

## Risks

- Большой рефакторинг может случайно изменить поведение.
- Перемещение кода может сломать импорты или тестовые mocks.
- Без декомпозиции задача станет слишком широкой для безопасной проверки.
